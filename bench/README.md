# NotebookFlow performance benchmark suite

Two reproducible micro-benchmarks that quantify two already-merged optimizations
in NotebookFlow. Both are written to be lifted directly into a paper's
methodology section: documented synthetic workloads, fixed seeds, warmup +
median-of-N protocol, captured machine context, and honest threats to validity.

- **Benchmark 1 — `SyncEngine.ingestNotebook` scaling** (TypeScript / graph-canvas)
- **Benchmark 2 — `DataBus` intermediate-DataFrame handling** (Python / engine)

Results from each run are captured under [`results/`](./results) as a
human-readable `<date>-<host>.md` table and a machine-readable
`<date>-<host>.json`, both prefixed with the machine context and the git commit
SHA the run was taken at.

> This directory is **not** part of any package build or test run. The
> graph-canvas Vitest config only includes `src/**/*.test.ts`, and the benchmark
> lives in `bench/` with its own explicit config, so `pnpm test` / CI never runs
> it. See [Isolation from CI](#isolation-from-ci).

---

## How to run

From the repo root, after `pnpm install` and (for Benchmark 2)
`uv --project engine sync --extra dev`:

```sh
# Both benchmarks + write results/<date>-<host>.{md,json}
node bench/run_all.mjs
```

Run them individually:

```sh
# Benchmark 1 — SyncEngine ingest (Vitest, graph-canvas package context)
pnpm --filter @notebookflow/graph-canvas exec vitest run \
  --config ../../bench/vitest.sync.config.ts

# Benchmark 2 — DataBus (engine Python env)
uv --project engine run python bench/databus_bench.py
```

When run standalone, each script writes its own JSON *fragment* into
`results/<date>-<host>-<bench>.fragment.json` (git-ignored). `run_all.mjs`
instead directs both fragments to a temp dir and merges them into the single
committed `results/<date>-<host>.{md,json}` pair.

Nothing in the product source tree is modified: the benchmarks import the
public `SyncEngine` / `MarkerParser` from `packages/graph-canvas/src/sync` and
the `DataBus` class from `notebookflow.core.databus` as-is.

## Benchmark 1 — `SyncEngine.ingestNotebook` scaling

### What we measure

`SyncEngine.ingestNotebook` (`packages/graph-canvas/src/sync/SyncEngine.ts`) is
the core notebook → graph synchronization. On every notebook save it re-parses
each cell's `# @node:` marker (`MarkerParser`), rebuilds the notebook's node
graph, and resolves **every** contract-binding wire across the workspace
(`recomputeAllWires`). For editor adapters it also runs on **every keystroke** in
a marker cell (the whole cell array is re-ingested). It therefore sits directly
on the interactive-latency path, and its scaling in the number of cells is the
claim the paper makes. The merged optimization replaced per-binding linear scans
in wire resolution with a name-resolution index rebuilt once per ingest, taking
a full-notebook ingest from O(n²) to ~O(n); this benchmark is the evidence that
ingest is now ~linear at interactive sizes.

We report two paths:

- **Fresh ingest** — a brand-new `SyncEngine` ingesting the whole notebook once
  (the notebook-open / file-save cost).
- **Re-ingest** — an already-populated engine re-ingesting the same notebook
  with a single cell's body mutated (the every-keystroke cost).

### Workload

Synthetic notebooks generated by `generateNotebook(cellCount)`
(`bench/sync_engine.bench.ts`), a pure function of the cell index (no
`Math.random`):

- **~80% marker cells + ~20% markerless filler.** Every 5th cell
  (`index % 5 === 4`) is a plain markerless code cell; the rest carry a canonical
  single-line marker.
- **Fully-wired linear chain.** Marker cells are named `Node0, Node1, …`; each
  marker node except the first declares `in=inp<-Prev.out` referencing its
  immediate marker predecessor and `out=out` so that reference resolves. The
  result is a chain of `nodes = floor(0.8 · cellCount)` nodes with `nodes − 1`
  resolvable wires (reported in the table).
- **Sizes (cells):** `[10, 25, 50, 100, 200, 400, 800, 1600, 3200]`.

Marker cells also carry a few lines of realistic body source; the marker line is
always the cell's first non-blank line, as the parser requires.

### Protocol

- **Warmups:** 3 (discarded) per size, per path.
- **Measured repetitions:** 9 → the **median** is reported (plus min/max).
- **Timing:** `performance.now()` around a single awaited `ingestNotebook()`
  call. Notebook generation and graph inspection happen **outside** the timed
  region. Adapter callbacks (`onCellPatch`, `onGraphUpdate`) are no-ops so we
  measure the engine, not a platform adapter's rendering.
- **Fresh path:** a new `SyncEngine` per repetition.
- **Re-ingest path:** one warm engine; each repetition mutates a marker cell near
  the middle (appends a comment line, so the graph is identical but the source
  genuinely differs — no no-op short-circuit) and re-ingests the full array.
- **Scaling characterization:** ms-per-cell at the largest size, and the
  fresh-median growth ratio as size ≈ doubles (≈2.0 ⇒ linear, ≈4.0 ⇒ quadratic).
- **Environment:** Vitest `node` environment, single-threaded, no isolation
  (`bench/vitest.sync.config.ts`), to minimize pool/timing overhead.

### Expected shape

Single-digit milliseconds at ≤ 100 cells; crossing ~100 ms only in the low
thousands of cells; doubling ratios clustering around 2 (linear), not 4.

## Benchmark 2 — `DataBus` intermediate-DataFrame handling

### What we measure

`DataBus` (`engine/notebookflow/core/databus.py`) stores the intermediate
outputs (mostly pandas DataFrames) that flow between pipeline nodes. The merged
optimization keeps DataFrames whose deep memory is **at or below**
`NOTEBOOKFLOW_SPILL_THRESHOLD_BYTES` (default **8 MB**) resident in memory (a
put-time deep copy that preserves the same mutation-isolation guarantee as the
spill path), and spills only larger frames to Parquet. Setting the threshold to
`0` forces **every** frame to spill — this exactly restores the previous
"always spill to Parquet" behaviour, giving a clean **before/after in one run**:

| Mode | `NOTEBOOKFLOW_SPILL_THRESHOLD_BYTES` | Meaning |
| --- | --- | --- |
| `forced_spill` | `0` | naive baseline (always Parquet round-trip) |
| `default` | unset → 8 MB | the optimization (small frames stay in memory) |

Because the threshold is snapshotted per-`DataBus` at construction, each mode
constructs its bus after setting/clearing the env var.

### Workload

`make_dataframe(n_rows)` (`bench/databus_bench.py`) builds a deterministic
~8-column mixed-dtype DataFrame (numpy seeded with `12345`): `int64`, `int32`,
`float64 ×2`, `float32`, `bool`, a low-cardinality string column, and a
high-cardinality label string column. The schema is fixed so that a given row
count always yields the same bytes, and specifically so that **50k rows
(~3.3 MB) stays in memory** under the default threshold while **500k rows
(~33 MB) spills** — exercising both code paths and demonstrating that large
frames are still correctly spilled.

Two scenarios:

- **A — single put+get latency.** Row counts `[1k, 50k, 500k]`, both modes.
- **B — sequential pipeline.** `N × (put+get)` at 50k rows for
  `N ∈ [50, 100, 300]`, both modes — the "hundreds of intermediate DataFrames"
  case. Every intermediate is retained (fan-through), so `default` mode holds
  `N` frames in RAM while `forced_spill` holds `N` Parquet files on disk.

### Protocol

- **Scenario A:** 3 warmups (discarded) + 9 measured repetitions per (rows,
  mode); the **median** put+get round-trip is reported (plus separate put/get
  medians and min/max). Each repetition uses a fresh store key, i.e. a distinct
  intermediate. We also record the stored size and whether the frame spilled
  (by inspecting the on-disk spill directory).
- **Scenario B:** the full N-intermediate pipeline is one timed unit; it is
  repeated `SEQ_TRIALS = 3` times and the **median total wall time** is reported
  (min/max also captured) to damp filesystem-I/O noise. **Peak Python memory**
  (`tracemalloc`, max across trials) and **on-disk spill bytes** (max across
  trials) are data-deterministic and reported alongside. Each trial does one
  discarded warmup round-trip first.
- **Timing:** `time.perf_counter()`.
- **Isolation:** every `DataBus` uses a fresh temp spill directory, removed
  afterwards.

### Expected shape

At 50k rows the in-memory `default` path is roughly **~50×** faster than the
`forced_spill` Parquet round-trip; at 500k rows both modes spill, so the speedup
is ≈ 1× (a correctness check that large frames still spill). Scenario B shows the
same order-of-magnitude wall-time win, plus the intended trade-off: `default`
uses ~0 disk but more RAM, `forced_spill` uses ~0 tracked RAM but hundreds of MB
of disk.

## Isolation from CI

- The graph-canvas package's `vitest.config.ts` includes only
  `src/**/*.test.{ts,tsx}`. The benchmark is `bench/sync_engine.bench.ts`
  (outside `src/`, and a `.bench.ts` not a `.test.ts`), run only via the
  explicit `bench/vitest.sync.config.ts`. So `pnpm test` → `turbo run test` →
  each package's `vitest run` never collects it.
- `tsconfig` for graph-canvas has `rootDir: ./src` and `include: ["src/**/*"]`,
  so `tsc -b` never compiles `bench/`.
- The Python benchmark lives in `bench/`, while `pytest` is configured with
  `testpaths = ["tests"]` in `engine/pyproject.toml`, so it is never collected
  by the engine test run either.
- Per-run JSON fragments are git-ignored (`bench/.gitignore`); only the merged
  `results/<date>-<host>.{md,json}` are committed.

You can confirm the exclusion locally: `pnpm --filter @notebookflow/graph-canvas
test` runs the package's unit tests only and does not execute the benchmark.

## Caveats / threats to validity

- **Single machine, single OS.** All numbers come from one Windows laptop
  (captured in each results file). Absolute timings are not portable across
  hardware; the *shape* (linear vs quadratic; in-memory vs spill ratio) is the
  transferable result.
- **Run-to-run variance.** These are consumer-laptop runs subject to CPU thermal
  throttling, background load, and OS filesystem caching. Parquet-heavy numbers
  (Benchmark 2 `forced_spill`) vary substantially between runs (tens of percent);
  the median-of-N (and Scenario B's median-of-trials) reduces but does not
  eliminate this. Treat the reported speedups as order-of-magnitude, not
  significant to their last digit. As a built-in noise calibration, the 500k-row
  case does identical work in both modes, so its ratio should be ≈ 1× — deviation
  there indicates the noise floor of a given run. The committed
  `results/<date>-<host>.{md,json}` is a **representative run** captured while the
  CPU was in a stable-frequency regime (the SyncEngine table is monotonic in
  cell count and the DataBus 500k ratio is ≈ 1×); the numbers reproduce in shape,
  not to the millisecond, on re-runs. The i7-1065G7 used here has a 1.30 GHz base
  / 3.90 GHz turbo, so a throttled window can shift absolute timings by up to ~3×.
- **Synthetic workloads.** Notebooks are uniform linear chains; real notebooks
  have branching/fan-out and irregular marker density. DataFrames are synthetic
  mixed-dtype tables; real intermediate schemas (and their Parquet
  compressibility) differ. The workloads are chosen to isolate the measured
  operation, not to reproduce a specific real pipeline.
- **GC / JIT.** JavaScript (V8) JIT warmup and GC pauses, and Python allocator
  behaviour, are only partially controlled by the warmups; occasional high
  `max` samples reflect GC pauses. Medians are used specifically to be robust to
  these.
- **`tracemalloc` under-counts native memory.** It traces Python-level
  allocations; large numpy/PyArrow buffers allocated in C may be under-counted,
  so Scenario B's peak RAM is a **lower bound** on true process RSS. It is still
  a valid *relative* signal (in-memory mode's peak grows with `N`, spill mode's
  stays flat).
- **pandas 3.x string dtype.** pandas 3.0 defaults to an Arrow-backed string
  dtype, which changes `memory_usage(deep=True)` and the spill/no-spill boundary
  versus older pandas. The exact byte sizes here are specific to the captured
  pandas/numpy versions.
- **Warm filesystem.** Parquet spill files land in the OS temp dir; a warm page
  cache makes reads faster than a cold-cache first touch. This biases the
  `forced_spill` numbers *optimistically* (i.e. the real-world win of the
  in-memory path is, if anything, understated).
